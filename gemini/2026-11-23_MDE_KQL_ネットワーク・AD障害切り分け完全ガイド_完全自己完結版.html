01

結論：MDEで障害切り分けは「極めて有効」だが、構造的限界を知って使う

ご経験された「毎時0分台の無線接続失敗（LDAP認証スパイク→ADユーザー不存在エラー）」の特定アプローチは、MDEの最も強力な強みである「全端末横断のタイムライン可視化」と「通信とプロセスの1対1紐付け」を最大限に活かした理想的な手法です。同様のアプローチは、ネットワーク帯域の輻輳（パッチ適用日の通信集中を含む）やAD障害、プロキシ/DNS障害の切り分けにも応用可能です。

【最重要制約】DeviceNetworkEvents には「転送バイト数（SentBytes / ReceivedBytes）」が存在しない

Microsoft Learn公式スキーマ（DeviceNetworkEvents table）の通り、MDEはセキュリティEDRでありパケットキャプチャやNetFlowコレクタではないため、「1つのTCPセッションで何MB/何GB通信したか」を直接集計するカラムを持ちません。したがって、「単一セッションで巨大な動画やISOファイルをダウンロードし続けているケース」はMDEのセッション数ランキングだけでは上位に現れないことがあります。

突破口（3段プロキシ指標）：帯域輻輳を切り分ける際は、①同時通信端末数（dcount(DeviceName)）、②更新CDN・WSUS・P2Pポート（7680）へのセッション生成頻度（count()）、③DeviceFileEvents との相関（SoftwareDistribution\Download や DeliveryOptimization\Cache への実ファイル書き込み検知）を組み合わせることで、パッチ適用日の帯域犯人を極めて高い精度で特定できます。

02

MDEスキーマ仕様と実務で必ずハマる「4大落とし穴」

KQLを書く前に、MDEセンサーがエンドポイントからどのようにテレメトリを収集し、どのカラムに何が入るのかを正確に理解しておく必要があります。ここを誤解すると「クエリはエラーなく動いたのに0件だった（原因を見逃した）」という致命的な空振りが起きます。

落とし穴 1：ActionTypeの名前を信じてはいけない
DnsConnectionInspected はプロセス名・URLが空になる

Microsoft公式の技術検証（Zenn Microsoft公式記事）でも指摘されている通り、DnsConnectionInspected は実環境では RemoteUrl や InitiatingProcessFileName の充足率が0%になる挙動があります。プロセスと通信先を確実に紐づけるには、ConnectionSuccess / ConnectionFailed を軸に組み、平時にQ14で充足率を確認するのが鉄則です。

落とし穴 2：svchost.exe のブラックボックス問題
WSUSもWUもDOも全部 svchost.exe に見える

Windows Update（wuauserv）、配信の最適化（DoSvc）、BITS（BITS）の通信元プロセスはすべて InitiatingProcessFileName == "svchost.exe" になります。必ず InitiatingProcessCommandLine（例：svchost.exe -k netsvcs -p -s DoSvc）からサービス名を抽出して分解する必要があります（後述Q6参照）。

落とし穴 3：プロキシ環境での RemoteIP / RemoteUrl 乖離
プロキシ経由時は RemoteIP がプロキシIPに集約される

明示的プロキシ（PAC/WPAD/WinHTTPプロキシ）を経由する環境では、クライアント端末のTCP接続先はプロキシサーバーになるため、RemoteIP がすべて社内プロキシIP、RemotePort が 8080 や 3128 になります。宛先判定は RemoteUrl を軸にし、プロキシバイパス（M365ローカルブレイクアウト等）との混在を意識してクエリを組みます。

落とし穴 4：テレメトリ集約とサンプリングの存在
全パケット・全イベントが100%転送されるわけではない

MDEセンサーは端末負荷とクラウド転送量を抑えるため内部的にイベントの集約・フィルタリングを行っています（MDE Telemetry & Custom Data Collection Rules解説）。絶対値ではなく「平常時ベースラインとの相対スパイク比」で判断するのが実務のコツです。

AD・認証・無線LAN（802.1X）障害の切り分け実践

ご経験された「毎時0分台だけ無線接続が失敗する → 1分単位の対DCプロトコル可視化でLDAP大量通信を発見 → 犯人プロセスを特定」という事例は、AD障害切り分けの王道パターンです。なぜ「毎時0分台」にAD障害や認証失敗が集中するのか、その典型メカニズムと再現・発展クエリを整理します。

典型原因 A：定時タスクの一斉発火

Windowsタスクスケジューラ、資産管理エージェント、独自バッチ、セキュリティ製品が「毎時00分（ランダム遅延なし）」で全端末一斉にADへLDAP照会・認証を実行し、DCのLDAPスレッドを枯渇させる。

典型原因 B：削除済IDのキャッシュ認証

資格情報マネージャー、サービス実行アカウント、または802.1X無線プロファイルに古い/削除済みユーザー情報が残り、毎時リフレッシュ時にADへ「存在しないユーザー」で認証要求を連打する。

典型原因 C：RADIUS/NPS再認証同期

無線LANコントローラやNPS（RADIUS）のセッションタイムアウト（例：3600秒）とAD側のLDAP遅延・応答タイムアウトが重なり、特定時間帯だけ802.1X認証が連鎖的に失敗する。

Q1対DC（Active Directory）1分単位 プロトコル別セッション可視化
用途：実体験された「毎時0分台のLDAPスパイク」のように、全端末からドメインコントローラー群へ飛んでいる通信を1分刻み・プロトコル別に時系列グラフ化します。dc_ips に自社のDC IP一覧を設定して実行してください。
// Q1: 1分ごとの対AD(DC) プロトコル別セッション可視化（毎時0分スパイク検知）
let dc_ips = dynamic(["10.0.0.10", "10.0.0.11"]); // ★自社のDC IPアドレスに置換
DeviceNetworkEvents
| where Timestamp > ago(6h)
| where RemoteIP in (dc_ips)
| where ActionType in ("ConnectionSuccess", "ConnectionFailed")
| extend AdProtocol = case(
    RemotePort == 389,   "LDAP (389)",
    RemotePort == 636,   "LDAPS (636)",
    RemotePort == 3268,  "GlobalCatalog (3268)",
    RemotePort == 3269,  "GlobalCatalog-SSL (3269)",
    RemotePort == 88,    "Kerberos (88)",
    RemotePort == 53,    "DNS (53)",
    RemotePort == 445,   "SMB/SYSVOL (445)",
    RemotePort == 135,   "RPC-EPM (135)",
    RemotePort >= 49152, "Dynamic-RPC (49152+)",
    strcat("Other (", tostring(RemotePort), ")")
)
| summarize SessionCount = count() by bin(Timestamp, 1m), AdProtocol
| render timechart
Q2特定時間帯（毎時0分台等）にLDAP/認証を連打している「犯人プロセス」特定
用途：Q1でスパイクが確認できた時刻帯（例：毎時00〜02分）に絞り込み、どのプロセス・親プロセス・コマンドライン・アカウントが何台からLDAP通信を発火させているかを特定します。
// Q2: 毎時00分〜02分台にDCのLDAP(389/636/3268)へ集中通信している犯人プロセス特定
let dc_ips = dynamic(["10.0.0.10", "10.0.0.11"]); // ★自社のDC IPアドレスに置換
DeviceNetworkEvents
| where Timestamp > ago(24h)
| where RemoteIP in (dc_ips)
| where RemotePort in (389, 636, 3268, 3269, 88)
| where ActionType in ("ConnectionSuccess", "ConnectionFailed")
| extend MinuteOfHour = datetime_part("Minute", Timestamp)
| where MinuteOfHour between (0 .. 2) // ★障害発生の分台に絞る（不要ならコメントアウト）
| summarize
    TotalSessions = count(),
    FailedSessions = countif(ActionType == "ConnectionFailed"),
    AffectedDevices = dcount(DeviceName),
    SampleDevices = make_set(DeviceName, 5),
    SampleCmdLines = make_set(InitiatingProcessCommandLine, 3),
    SampleAccounts = make_set(InitiatingProcessAccountName, 5)
    by InitiatingProcessFileName, InitiatingProcessParentFileName, InitiatingProcessFolderPath, RemotePort
| order by TotalSessions desc
Q3無線LAN（SSID）別 × 接続失敗・ログオン失敗のクロス分析
用途：「特定の社内Wi-Fi（SSID）に繋がっている端末だけ認証や通信が失敗していないか？」を DeviceNetworkInfo の ConnectedNetworks JSONを解析して切り分けます。
// Q3: 接続中Wi-Fi(SSID)ごとのネットワーク接続失敗(ConnectionFailed)と対象ポート集計
let WifiDevices = DeviceNetworkInfo
| where Timestamp > ago(6h)
| where NetworkAdapterType == "Wireless" and isnotempty(ConnectedNetworks)
| mv-expand Net = parse_json(ConnectedNetworks)
| extend SSID = tostring(Net.Name), NetCategory = tostring(Net.Category)
| where isnotempty(SSID)
| summarize arg_max(Timestamp, SSID, IPAddresses, DnsAddresses) by DeviceId, DeviceName;
DeviceNetworkEvents
| where Timestamp > ago(6h)
| where ActionType == "ConnectionFailed"
| join kind=inner WifiDevices on DeviceId
| summarize
    FailCount = count(),
    AffectedDevices = dcount(DeviceName),
    TopProcesses = make_set(InitiatingProcessFileName, 5)
    by SSID, RemoteIP, RemotePort, RemoteUrl
| order by FailCount desc
| take 50
Q4【MDI併用】AD側の「ユーザー不存在」認証失敗と端末側プロセスを突合
用途：Microsoft Defender for Identity（MDI）導入時、DC側で観測された IdentityLogonEvents の失敗理由（UnknownUserName等）とMDEの DeviceNetworkEvents を同一端末・同一分で結合し、犯人プロセスを特定します。
// Q4: MDI(IdentityLogonEvents)の認証失敗とMDE(DeviceNetworkEvents)の端末プロセスを1分単位で突合
let AdFailures = IdentityLogonEvents
| where Timestamp > ago(6h)
| where ActionType == "LogonFailed"
| where Protocol in ("Ldap", "Kerberos", "Ntlm", "Radius")
| extend TimeBin = bin(Timestamp, 1m), SourceDevice = tolower(tostring(split(DeviceName, ".")[0]))
| summarize
    AuthFailCount = count(),
    FailureReasons = make_set(FailureReason, 5),
    TargetAccounts = make_set(AccountName, 5)
    by TimeBin, SourceDevice, Protocol, DestinationDeviceName;
let EndpointLdap = DeviceNetworkEvents
| where Timestamp > ago(6h)
| where RemotePort in (389, 636, 3268, 88)
| extend TimeBin = bin(Timestamp, 1m), SourceDevice = tolower(tostring(split(DeviceName, ".")[0]))
| summarize
    Processes = make_set(InitiatingProcessFileName, 5),
    CmdLines = make_set(InitiatingProcessCommandLine, 3)
    by TimeBin, SourceDevice;
AdFailures
| join kind=leftouter EndpointLdap on TimeBin, SourceDevice
| project TimeBin, SourceDevice, DestinationDeviceName, Protocol, AuthFailCount, FailureReasons, TargetAccounts, Processes, CmdLines
| order by AuthFailCount desc

Q5【最重要】パッチ適用日「7大更新トラフィック」自動分類＆5分単位トレンド可視化
用途：「今まさに帯域を食っているのはWSUSか？インターネットのWindows Updateか？M365 Appsか？Teams/Edgeか？」を同時通信端末数（dcount(DeviceName)）で一発グラフ化します。

let wsus_ips = dynamic(["10.0.1.50", "10.0.1.51"]); // ★自社WSUSサーバーIPに置換

| where Timestamp > ago(12h)
| where ActionType in ("ConnectionSuccess", "ConnectionFailed")
| extend UpdateCategory = case(

        or RemoteUrl has_any ("msedge.api.cdp.microsoft.com", "msedge.b.tlu.dl.delivery.mp.microsoft.com"),

Q6svchost.exe の中身を暴く！Windowsサービス別（wuauserv / DoSvc / BITS）通信分解
用途：svchost.exe のコマンドラインから -s サービス名 を抽出し、Windows Update（wuauserv）・配信の最適化（DoSvc）・BITS を宛先別に分解します。
// Q6: svchost.exeのコマンドラインから実サービス名(-s)を抽出し、宛先URL/ポート別に分解
DeviceNetworkEvents
| where Timestamp > ago(4h)
| where InitiatingProcessFileName =~ "svchost.exe"
| where ActionType == "ConnectionSuccess"
| extend ServiceName = extract(@"-s\s+([^\s]+)", 1, InitiatingProcessCommandLine)
| extend ServiceGroup = extract(@"-k\s+([^\s]+)", 1, InitiatingProcessCommandLine)
| extend ResolvedService = iff(isnotempty(ServiceName), ServiceName, strcat("Group:", ServiceGroup))
| where ResolvedService in~ ("DoSvc", "wuauserv", "BITS", "AppXSvc", "ClipSVC", "Group:netsvcs")
| summarize
    Sessions = count(),
    UniqueDevices = dcount(DeviceName),
    SampleUrls = make_set(RemoteUrl, 5),
    SampleIPs = make_set(RemoteIP, 5)
    by ResolvedService, RemotePort, RemoteIPType
| order by UniqueDevices desc, Sessions desc

// Q7: パブリックInternet上のWindows UpdateダウンロードCDNへ直接通信している端末を摘発

Q8配信の最適化（TCP 7680）による「WAN越え・別サブネット間P2P」帯域圧迫の検知

// Q8: 配信の最適化(TCP 7680)で異なる/24サブネット(別拠点)へWAN越えP2P通信している箇所を検知
DeviceNetworkEvents
| where Timestamp > ago(12h)

Q9帯域詰まり発生時の「総合犯人ランキング」（拠点サブネット × プロセス × 宛先ドメイン）
用途：特定拠点（例：10.20.x.x）が激重になった際、直近1時間の「プロセス（svchost分解済）× 宛先ドメイン × 同時端末数」を一覧化します。
// Q9: 特定拠点(サブネット)における帯域輻輳時の「プロセス×宛先」総合犯人ランキング
let target_prefix = "10.20."; // ★調査したい拠点のIPプレフィックス（全社なら "" にする）
DeviceNetworkEvents
| where Timestamp > ago(1h)
| where ActionType == "ConnectionSuccess"
| where isempty(target_prefix) or LocalIP startswith target_prefix
| extend TargetDest = iff(isnotempty(RemoteUrl), RemoteUrl, RemoteIP)
| extend ServiceName = iff(
    InitiatingProcessFileName =~ "svchost.exe",

    InitiatingProcessFileName
)
| summarize

    UniqueDevices = dcount(DeviceName),
    AvgSessionsPerDevice = round(toreal(count()) / dcount(DeviceName), 1),

クエリ最適化・クォータ回避 ＆ パッチ適用日の恒久対策

Advanced Hunting クォータ・制限事項（公式仕様）
  • データ保持期間：Defender XDR標準で過去30日間（長期保持はSentinel連携）。
  • 結果表示上限：ポータルUIで最大100,000行（ガイドモードは10,000行）。必ず summarize で集約して返す。
  • 実行タイムアウト：1クエリ最大3分。DeviceNetworkEvents は最も巨大なテーブルのため無条件検索は即タイムアウト。
  • CPUクォータ：テナント規模に応じた15分サイクルのCPU枠あり。超過時はHTTP 429で一時ブロック。
緊急障害時にタイムアウトさせないKQLチューニング5鉄則
  • ① Timestamp を最初に極限まで絞る：ago(1h) や between(...) を1行目に置く。
  • ② contains ではなく has / has_any：トークンインデックスが効くため数倍〜数十倍高速。
  • ③ ActionType と RemotePort で先に削る：重い正規表現 extract() や parse_json() は行数を減らした後に行う。
  • ④ 大文字小文字を区別する演算子を優先：完全一致で良い箇所は == を使う。
  • ⑤ join は小さいテーブルを左側に置く：先に summarize で行数を圧縮してから結合する。

可視化の先へ：パッチ適用日の帯域輻輳を根絶するWindows管理者チェックリスト

対策 1：配信の最適化（DO）とグループID設計

ダウンロードモードを「LAN（1）」または「グループ（2）」にし、DOGroupIdSource をADサイト等で拠点単位に固定。帯域上限ポリシーでWAN越えP2Pを完全遮断。

対策 2：Microsoft Connected Cache (MCC) 導入

WUfB・M365 Apps・Teams・Edgeの更新をインターネット経由で運用する場合、各拠点にMCCキャッシュノードを配置し、インターネット回線負荷を劇的に削減。

対策 3：WSUS環境での意図せぬDual Scan遮断

Q7でインターネット流出端末を特定し、「Windows Updateインターネットの場所へ接続しない（DoNotConnectToWindowsUpdateInternetLocations）」や更新ソースポリシーの競合を解消。

対策 4：M365 Apps・Teams・Edgeの段階展開

全社一斉更新を避け、更新リングを分散。M365 Appsは「月次エンタープライズチャネル」＋配信の最適化連携を有効化し、パッチ適用日のピークを平準化。
